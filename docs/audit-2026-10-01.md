# Roxy Suite audit — October 1, 2026

Started October 1; completed October 2, 2026. Findings apply to the inspected revision, not later changes.

## Overall assessment

The suite has useful, genuinely integrated workflows and does not need a wholesale rewrite. Its main weakness is that safeguards are often correct for one request at a time but incomplete when two requests overlap, a dependency fails, or data changes between steps. Stabilize those boundaries before expanding automation.

**Recommended next work:** first protect ticket eligibility/refunds and booking payments/collisions; in parallel verify financial-report arithmetic and social approval/retry safety. Then unify atomic seat/admission/order decisions and correct reporting, scheduled-job reliability and data-quality warnings. Smaller privacy, escaping, navigation and form-completeness fixes can be released separately after focused tests. Keep prize fulfillment disabled until repaired. None of these recommendations authorizes changing production as part of this audit.

This is a review, not a repair or deployment. No real orders, payments, admissions, emails, or stock updates were generated for testing. Findings distinguish directly demonstrated defects, code-confirmed edge cases, compatibility risks, and optional business improvements. A code-confirmed race is not evidence that customers have already encountered it.

Audit baseline: local `master`, commit `910530d3bc77e17ac2dc267bac2bdadd6b5fae71`, Suite 1.0.16. Repository was clean and synchronized with its remote at inspection. Source references below are relative to `C:/Users/joker/Documents/GitHub/roxy-suite/` and refer to this baseline.

## Verification and limitations

- Reviewed shared bootstrap, administration, health checks, updater, membership dashboard, Member Check, Arcade and its three games, Inventory, and the specialist reviews recorded below for Show Tickets, Will Call, Event Booking, Requested Showings, Grosses, and Social Publisher. Legacy NFC redirects are included in the bootstrap review.
- Live server: PHP CLI 8.3.35, WordPress 7.1.2, WooCommerce 11.1.2, Subscriptions 9.2.0. All 63 deployed PHP files passed syntax checks. This is not a guarantee that every runtime business path works.
- Existing standalone inventory regression suite passed against deployed inventory classes, using fake database/network/mail functions: order transitions/cancellation, count pagination, stock-state filtering, preserving costs, failed-page preservation, silent nightly failure, email instructions/recipients and forwarding-token separation.
- Reproduced PHP form truncation with a harmless 170-product form: only 167 vendor fields survived; the last accepted row lacked its target field and the current save handler would replace it with zero. Server CLI `max_input_vars` is 1,000; confirm the web PHP setting too. Live Products currently has 143 tracked active products, of which 34 have zero cost. This is a growth hazard, not a claim that today's 143-row form already exceeds the limit.
- Reproduced fixed-interval daylight-saving drift: 11 p.m. October 31 plus 86,400 seconds becomes 10 p.m. November 1 in Los Angeles.
- HPOS is currently disabled. Compatibility findings concern a future storage change, not an existing HPOS outage.
- Arcade rewards and automatic fulfillment are both disabled live. Prize defects are dormant until enabled.
- Deployed source hashes matched the inspected repository for the principal modules. Health Check has a small real drift: the live copy lacks the local daily booking-health cron check. Extra older PHP/JS files exist on the server; existence alone does not prove that they execute.
- Nightly inventory/grosses and other suite cron events are registered. No user-crontab entry referencing `wp-cron` was found, but hosting-level scheduling was not ruled out. Do not conclude that cron is broken from that observation.
- No destructive load tests, simulated simultaneous live purchases, provider publishing, refunds, prize creation, browser checkout, or real email-delivery tests were performed. These require staging and sandbox credentials. No claim is made that the suite is vulnerability-free.

## Priority and change-risk scale

**P1:** money, unauthorized state change, duplicate orders, or incorrect admissions; address first. **P2:** reporting accuracy, reliability, or growing operational risk. **P3:** maintainability or convenience.

Correction risk is separate: **Low** means localized behavior with limited downstream effects; **Medium** means a workflow, scheduling, or storage change requiring integration tests; **High** means payment, capacity, or historical-data behavior that needs staging, reconciliation and rollback planning. None means zero risk.

### Accounting rules to settle before changing historical numbers

- **Nominal versus collected gross:** reporter `:1155` deliberately multiplies ticket counts by configured prices (documented in Grosses Settings `:773`). Preserve the intended studio-reporting rule or show separate nominal/collected metrics; don't silently redefine it. Historical reruns can use new prices. Change risk High.
- **Purchase-time attribution:** reporter `:1318` chooses a nearby showing within ±90 minutes, which can omit advance sales or misattribute overlapping titles; `:1245` includes nonpublic statuses and next-midnight boundaries. Prefer explicit purchased-show identity where available and flag uncertain matches. Change risk High.
- **Classifier settings:** Grosses Settings `:155` advertises configurable inclusion/exclusion terms, but reporter `:1212` uses fixed classification. Align the implementation and settings, with custom-term regression cases. Change risk Medium.
- **Reporting month:** Workbook `:196,558` assigns the whole week to its start month. This is not calendar-month attendance. Label the policy or implement daily calendar-month aggregation after agreement. Change risk Medium.
- **Studio overrides:** Metadata `:51,69` puts built-in overrides ahead of configured ones; workbook `:981` uses configured overrides. Make precedence consistent. Change risk Low.

Further verification: actual workbook formulas/cached values and protection; whether WooCommerce and Square can contain the same sale; API/token expiry/permission/version compatibility; thumbnail URL/path boundaries. ## Safe remediation approach

1. Create a staging copy with external email redirected and live payment/order/publishing side effects disabled. Back up database and files, then verify that restore is usable; do not rely on a backup listing alone.
2. Add regression cases for each confirmed defect before correcting it. Payment, admission, order submission and scheduling tests should include two simultaneous requests, timeouts and retries—not only successful single clicks.
3. Release focused changes in small batches. Avoid one giant refactor. Retain current settings, inventory rules, order history, active membership cards and ticket links.
4. Deploy from one reviewed artifact; record revision and verify source parity. Inspect operational dashboards after release, then check the next scheduled run.
5. Keep an explicit rollback path for migrations and payment/capacity changes. A code rollback alone cannot undo incorrect payments, sent orders or changed historical records.

For scheduled work, first verify whether the host already supplies a reliable runner. WordPress cron normally depends on page requests, but hosting can supply its own scheduler; configure one only after checking to avoid duplicate runners. [WordPress scheduler integration](https://developer.wordpress.org/plugins/cron/hooking-wp-cron-into-the-system-task-scheduler/).

Preserve the user's communication policy: inventory emails occur only on order submission. A dashboard warning/job log is appropriate for stale/failed pulls; do not add nightly stock or readiness emails without a new request.
