# Stability checkpoint 66 — Square refund cash-event normalization

G2 remains in progress. The request-local Square refund snapshot now exposes a separate `completed_return_financial_refunds()` projection for completed, return-linked payment refunds. It retains Square refund/payment/return-order/location identities and integer USD cents, and derives the reporting date from the completed refund's latest Square `updated_at` timestamp in the configured report timezone. Pending, rejected and failed refunds are excluded. Invalid identities, currencies, amounts or timestamps fail closed when the financial projection is requested. This does not yet include unlinked or non-return refunds.

This seam is intentionally separate from the sale-day ticket reconciliation. It does not write a database ledger, change Grosses totals, change emailed reports, or rewrite historical data. Square documents `updated_at` as the timestamp the refund was last updated and `status` as its current state; for a currently completed refund, this is the available timestamp used here as the completion-date proxy. If Square changes a completed refund later, stable identity must make a future ledger upsert idempotent and preserve the evidence of the changed record.

Isolated regression coverage verifies Pacific date-boundary attribution, integer cents, stable identities, and fail-closed malformed date/unsupported currency handling. The first hosted run caught that malformed-data assertions were mutating a fake provider after the snapshot had already copied its values; the fixture now reloads a fresh snapshot for each malformed case. Hosted runs `37739669665` and `37740286261` passed PHP syntax on 8.0–8.4 and all configured isolated regressions, including the expanded Square refund snapshot suite. The projection labels Square's `updated_at` accurately rather than asserting the API provides a dedicated completion timestamp. No production database, refund, payment, report, or email was changed. No deployment is claimed.

Remaining before G2 can close: persist an idempotent dated ledger with provenance and update financial-only reporting surfaces; bound/refine historical refund discovery; handle custom-amount and exchange returns; reconcile live-door and WooCommerce refunds; test migrations and historical replay on isolated populated tables; then validate affected dashboards/exports on the live site without changing historical production records.
